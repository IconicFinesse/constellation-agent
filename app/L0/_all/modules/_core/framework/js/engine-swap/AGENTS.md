# AGENTS

## Purpose

`engine-swap/` is the shared transport and tool-registry layer for the LLM action-envelope upgrade, following the `execution-blocks.js` precedent: one pure, shared implementation under `_core/framework/js/`, consumed by both agent surfaces.

P1 built the transports, the registry skeleton and the shadow observer. P2 adds the DISPATCH PIPELINE and the launch tool inventory on the onscreen surface, behind a second default-off flag (`ENGINE_SWAP_DISPATCH`). With dispatch OFF nothing here runs and chat is byte-identical to the text protocol. With dispatch ON a tools-capable config runs Tier 1: the model is offered typed tools, its calls are validated, coerced, risk-classified and executed against the existing handlers, results return as structured tool messages, and the loop runs until a plain-text answer. A config without the tools capability stays on Tier 3 with one diagnostics line.

Streaming tool-call assembly and sequential parallel dispatch shipped in P3 (see the streaming section below). Admin-surface convergence (P4), prompt caching (P5) and rollout (P6) are deliberately absent here.

## Ownership

- `capabilities.js`: the ONE capability-resolution seam. Provider truth, model rules, transport clamps, and the per-session capability log line.
- `canonical.js`: the canonical internal action shape (OpenAI chat-completions messages/tools/tool_calls) plus canonical to wire transforms.
- `transports.js`: per-provider OpenAI-shape adapter scaffolding (NeuralWatt, OpenRouter, Synthetic, OpenAI). Assembly only, no network calls.
- `tool-registry.js`: tool records as data, deterministic visible-tool-list assembly, strict-schema projection, the dispatch-table stub, and per-tool stats.
- `shadow-normalize.js`: the shared normalization rules for shadow artifacts (own-user path collapse, recursive key sorting, code by hash plus first line, payload redaction).
- `shadow-classifier.js`: the closed nine-class diff enum, display-only detection, and verdict computation for the `ca.shadow-diff/1` gate.
- `shadow-session.js`: shadow run state and the three contract artifacts (manifest, sessions, summary) with an injectable emit sink.
- `shadow-projector.js`: derives the Tier 1 call list from executed Tier 3 block bodies without evaluating them.
- `config-flag.js`: the `ENGINE_SWAP_SHADOW` and `ENGINE_SWAP_DISPATCH` flags, the dispatch x shadow session plan, and tier resolution, read through the app's existing runtime-parameter system.
- `dispatch-errors.js`: the closed five-class error taxonomy (`validation` / `coercion` / `execution` / `api` / `policy`). Every error carries a human line AND a model-facing retry hint; a prose-only error is a defect.
- `dispatch-validation.js`: stage 1. Structural JSON-Schema checks (required, unknown fields, enum, minimum) plus arguments-JSON parsing. Type shape is NOT judged here.
- `dispatch-coercion.js`: stage 2. The closed repair table for known-harmless shape slips, and an honest rejection for richer wrong shapes. Owns type shape by design so its rejection path is reachable.
- `dispatch-pipeline.js`: the ordered pipeline (validation -> coercion -> risk -> execution -> structured result), argument adapters onto the shipped `space.api` handlers and the execution context, and `formatToolResultForModel`.
- `destructive-gate.js`: the v1 consent affordance state machine (`idle -> held -> confirmed | denied | cancelled`) with a guaranteed exit from every state.
- `history-shapes.js`: the ONE reader for both history shapes (legacy text protocol and typed tool entries), the writer constructors, the persistence mapping pair, the canonical <-> typed conversions, and the render/prompt projections.
- `prompt-shape.js`: the Tier 1 prompt shape (the api contract card retires, the fence contract stays) and the deterministic tool-list diagnostics line.
- `tool-turn-loop.js`: the Tier 1 loop: send a turn, dispatch its calls STRICTLY SEQUENTIALLY in returned order, feed the structured results back, stop on plain text, iteration cap, stop request, transport failure or a held destructive call. Three contracts are load-bearing: every announced `tool_call_id` is answered exactly once (a mid-batch failure answers its own call and the rest still run; the siblings of a held call are answered `deferred:`), a call whose streamed arguments never completed is refused **before any call enters the message list**, and `isStopRequested` is consulted between iterations *and* after a transport failure, so a stop is reported as `stopped` rather than surfacing as an error. The repeat note escalates on every failure path (audit-2 N2).
- `tier1-session.js`: one session object composing registry, transport, gate, pipeline and loop, plus the completion parse that accepts BOTH an assembled stream result and a raw completion payload, the `stream: true` tool-turn request, and the post-hold continuation.
- `stream-assembly.js`: the ONE streaming tool-call assembler: per-index argument fragment accumulation and the completeness verdict (`argumentsComplete`) the loop dispatches on. Pure leaf, no imports.

The live-path bridges live with their surface: `_core/onscreen_agent/engine-swap-shadow.js` (P1 observation, lazy loading, capability line, flush seam) and `_core/onscreen_agent/engine-swap-dispatch.js` (P2 tier decision and turn runner). Both are thin by construction: surface code only imports and calls, and no dispatch logic lives surface-side.

## Local Contracts

### Flag And Inertness

- Two flags exist, both declared in `commands/params.yaml` as frontend-exposed booleans with `default: false` and read through `space.config.get(...)`. No second settings store: `ENGINE_SWAP_SHADOW` (P1 observation) and `ENGINE_SWAP_DISPATCH` (P2 master gate for the tool path).
- OFF must stay genuinely inert: the bridge statically imports only the dependency-free `config-flag.js` leaf, then resolves the flag synchronously and returns before importing the engine-swap machinery, allocating a session, logging, or writing anything. The live surface (`store.js`) does statically import `history-shapes.js` and `engine-swap-dispatch.js` on every session, so the precise claim is **loads no dispatch machinery when off**: both modules are inert without the flag, and neither pulls in the loop, pipeline, gate, transports or registry.
- ON must not change behavior either. Tier 3 executes exactly as before; the layer observes and records.
- A flag read that throws resolves OFF; observation failures log once and never break a turn.
- Dispatch OFF is inert for the tool path too: the store resolves the plan synchronously and returns to the untouched text protocol before importing any dispatch module.

### Capability Seam

- Exactly one provider-truth table exists in the product. Future provider-management work consumes this seam instead of introducing a second table.
- Resolution is a pure function of (provider, model): provider defaults, then provider-scoped model rules, then transport clamps.
- Unknown providers resolve to the conservative row with every optional capability off, which keeps such a config on Tier 3 rather than guessing.
- Model rules name their provider; the same model id on another provider never inherits capability.
- A transport cannot carry what it cannot express: a capability flag resolved true against a transport that declares no support is clamped off.
- The per-session capability log line names provider, model, tier, and all five flags.

### Registry And Prefix Determinism

- Tool records are data: `{ name, description, schema, riskClass, handler, source, deferrable }`.
- Visible-tool-list assembly is a pure function of (config, model) with canonical (alphabetical) ordering, so the same config always produces the same list, order, and hash. Session-varying data never enters the list, because the list is half the cacheable prefix.
- Tool descriptions are release-versioned content: editing one is a cache-invalidating change.
- The dispatch-table stub never executes anything. Its honest answer in P1 is `{ dispatched: false }`.
- Launch schemas mirror live server truth, not prose. `tests/engine_swap_registry_test.mjs` reads `ensureValidWriteOperation`, `ensureValidWriteEncoding`, and the `server/api/file_*.js` sources so a written-contract drift fails the build (the BUG-006 lesson).
- Handler refs are identifiers too: a handler is either a real `space.api.<method>` on the api-client surface or a `/modules/<path>#<symbol>` ref that must resolve to a real function in that module. The same suite asserts every ref, so an invented namespace fails the build instead of waiting for P2.

### Tier Selection And The Flag Matrix

- Dispatch is the master gate. With it OFF a session resolves tier `none` and nothing changes. With it ON the tier comes from `capabilities.js` alone: `tools` true -> Tier 1, otherwise Tier 3 with ONE diagnostics line. A session never changes tier mid-loop; a session object is created per send.
- The dispatch x shadow interaction is pinned by `tests/engine_swap_dispatch_flag_test.mjs`, cell by cell. On a real Tier 1 session shadow observation is SUPPRESSED (`shadowActive: false`) even when the shadow flag is on, because a Tier 1 turn executes no Tier 3 blocks and an empty diff would be a false pass rather than evidence. On a Tier 3 session shadow keeps observing.
- A local (browser-inference) provider resolves Tier 3 explicitly: there is no HTTP tool transport to send a tool list to.

### Dispatch Pipeline

- Stage order is mechanical and observable: validation -> coercion -> risk -> execution -> structured result. Every outcome carries `stages`, so a call that failed validation provably never reached coercion or a handler.
- Validation owns STRUCTURE (required fields, unknown fields, enum membership, minimums). Coercion owns TYPE SHAPE. A wrong type is always handed to coercion, which repairs the declared known-harmless slips or rejects the call before execution; repaired values are re-checked structurally so a coerced value cannot slip past an enum or a minimum.
- The coercion table is closed and data-driven (`KNOWN_HARMLESS_SLIPS`): numeric-as-string, boolean-as-string, one scalar wrapped in a single-element array, a lone `{ encoding }` object, and an explicit null for an optional field. Anything richer is rejected, because broad coercion would turn an intended append into a silent overwrite.
- Handlers are the shipped capabilities: `space.api` file shorthands and the execution context's `execute(code)` for `run_code`. Nothing here re-implements a file operation or an executor, and the fence contract inside `run_code` is unchanged.
- The error taxonomy is closed: `validation` / `coercion` / `execution` / `api` / `policy`. Every error carries a human line and a model-facing retry hint; `formatToolResultForModel` is the single formatter and a prose-only error is a defect.

### Destructive Gate (D3: inline confirm)

- `file_delete` is the only `destructive` tool at launch. Its call is HELD, never auto-executed, and the model is told HELD (not failed) with an explicit "do not retry".
- The state machine is small and total: `idle -> held -> confirmed | denied | cancelled`. Every terminal state is reachable without user input (`cancelHeld()` runs on stop, chat clear and session end), so a hold can never wait forever.
- Confirm re-enters the pipeline at execution only, so the arguments the human saw are the arguments that execute, and a second confirm settles nothing.
- The gate is a consent affordance, not a security boundary: the same deletion inside `run_code` is ungated by construction. Never advertise it as a boundary.

### History Shapes (both, forever)

- ONE reader: `readHistoryEntry` / `readHistoryEntries` / `describeHistoryEntryForRender`. No consumer branches on history shape itself.
- Legacy text-protocol entries are never rewritten and render exactly as before. Typed entries (`tool_call`, `tool_result`) render through the same execution chip via `projectHistoryEntryForDisplay`, and project onto plain text for a Tier 3 prompt via `projectHistoryEntryForPrompt` so a conversation started on Tier 1 is still visible after a config change.
- Writers emit only typed entries (`createToolCallEntry`, `createToolResultEntry`); the persistence write/read pair (`serializeTypedHistoryFields`, `normalizeTypedHistoryFields`) lives here so the store and the reader cannot drift, and returns `{}` for a legacy message so its stored shape is byte-identical to before.
- Exactly one tool result may exist per call id. A settled hold REPLACES the held result rather than appending a second one.

### Typed History Order (transcript fidelity)

- `canonicalMessagesToTypedEntries` maps an assistant message carrying BOTH `content` and `toolCalls` to its narration as a plain `message` entry FIRST, then one `tool_call` entry per call in call order. `tool` messages continue to map to `tool_result`. The per-iteration stored order is therefore assistant text -> tool_call(s) -> tool_result(s) -> next assistant text.
- This is a WRITER path only. A narration entry IS the plain assistant message shape the reader already handles, so no reader branch was added, no stored history is rewritten, and the dual-shape discipline stays intact.
- Dropping the narration is a REGRESSION, not a simplification: it discards prose the user watched stream, and because the renderer draws stored order faithfully, it stacks every iteration's chips at the top of the turn with no assistant anchor between them (owner-reported live defect, 2026-10-27).
- A narration-less tool turn still emits its calls only, and `assistant-<index>` is the id convention on both assistant paths.
- `buildMessageDisplayGroups` in `thread-view.js` is the render-side counterpart and is order-faithful; it is exported so the order contract is assertable at the real code path. Reordering or hoisting chips there is a regression against this contract.
- It is NOT literally one group per stored entry. Its execute-section branch PEEK-AHEADS and folds the next entry into the card as that card's output pane, which is correct for the text protocol (whose execution follow-up is `{role:"user", kind:"execution-output", content:"execution ..."}` written directly under its message) and is EXCLUDED for typed entries. `projectHistoryEntryForDisplay` marks its projections `typedTool: "call" | "result"` and the peek-ahead refuses a marked entry, because a typed chip is a row of its own and never another message's pane. Without the exclusion, a narration containing an execution separator swallowed the tool-call chip that followed it and then settled `check_circle`/`is-success` over output that never ran (re-audit blocker, 2026-10-27).

### Tier 1 Streaming Preview Accumulation

- The surface keeps ONE preview slot per turn and APPENDS to it across iterations. It resets only on the first request of a turn, and once more at the start of a corrective retry (a separate attempt); iterations are separated by a blank line so two narrations do not run together. Clearing it per request made iteration 1's prose blink out the moment iteration 2 started.
- The slot stays strictly outside `this.history` (render projection only), is never serialized, and is cleared exactly once in the turn's `finally`, so commit, hold, error, stop and a thrown transport all exit through one clear.
- Deltas reach it through the surface's `onDelta` hook; the loop emits no delta event, so this is surface-owned by construction.

### Tier 1 Prompt Shape

- On a Tier 1 session the `api contracts` card retires from the system prompt: the contracts now live in the tool schemas, where they are enforced instead of recited.
- The old-idiom CORPUS also retires (`TIER1_DROPPED_SECTION_HEADINGS` = `traces`, `task examples`): several hundred lines of `_____javascript` + `space.api.*` demonstration, which taught the retired text protocol by example. Measured on the shipped file: 26.5k chars / 42 separators -> 10.5k chars / 11 separators, and the 11 survivors are contract and negation lines inside the retained sections, not demonstrations.
- `TIER1_RETAINED_SECTION_HEADINGS` (`known helpers`, `final rule`) is LOAD-BEARING. After the cut both must still be present or the prompt is not cut at all. It was previously declared, exported and never read, so the sections it named were protected by luck; the verification suites now fail if the guard is removed.
- Sections are removed by heading bounded by the NEXT KNOWN top-level heading (`PROMPT_TOP_LEVEL_HEADINGS`), not by an indent heuristic. `task examples` starts its body with a NON-indented line, so an indent-bounded scan removes the title and leaves every example — a diff that looks like a cut while teaching the old idiom untouched.
- The fence contract line stays on every tier (it governs `run_code` displays and Tier 3), and role/behavioral norms (`base law`, `rules`, `invalid`) are untouched. A prompt that would lose the fence marker is not cut at all (fail safe).
- Tier 3 prompts are returned byte-identical.
- Tier 1 then appends ONE steering leg (`TIER1_STEERING_MARKER`, `appendTier1Steering`): act by calling a tool, the fenced/separator display form only SHOWS code and never runs it, and it is for code the user explicitly asked to see. This exists because the P2 live run answered a file request with separator prose — the prompt's separator vocabulary was the only acting idiom the model saw. The leg constrains which channel ACTS; it never retires display, so a show-me-code answer still produces no tool call (BUG-007). It is idempotent by marker (re-shaping cannot stack duplicates) and sits behind the same fence-marker fail-safe. `tier3` and `none` are still returned byte-identical, asserted by the suite.

### Tier 1 Wire Hygiene (the P2 live hotfix-2 cause)

- THE finding, from the owner's devtools capture plus an A/B on the real endpoint: the conversation handed to a Tier 1 model carried the PROTOCOL ENVELOPE as message content (`_____framework\ncheck user detail`, `_____framework\nstart of new conversation...`, `_____user\nRead the file notes.txt`) AND a separator-form assistant demonstration (`Fetching user detail...` + `_____javascript` + `space.api.userSelfInfo()`). With the identical 5-tool list, `stream:false` and `deepseek-v4.1-flash`, that shape returned `finish=stop` with NO tool call and answered `Reading notes.txt from your root now...` + separator + `space.api.fileRead`; the same conversation stripped to plain user text returned `finish=tool_calls` with a typed `file_read`. The model imitates what it is SHOWN.
- `wire-hygiene.js` is the ONE seam, and it is a pure function: `sanitizeTier1WireMessages({ messages, envelopeMarkers, findSeparatorIndex })`. Envelope markers are stripped (a marker glued to text loses only the marker token, so the user's actual request survives); a separator-bearing assistant turn is PROJECTED to its narration plus `(code shown, not executed)`, or DROPPED and counted when only code remains. It reports `changed`, `dropped` and per-reason counts so a shorter wire is explicable rather than mysterious.
- Both vocabularies are INJECTED, never copied: `ONSCREEN_AGENT_PREPARED_MESSAGE_BLOCK` from `_core/onscreen_agent/llm.js` and the shared fence-aware `findExecutableSeparatorIndex`. A second copy of either is the BUG-007 anti-pattern. A fenced separator is display text and is never projected away.
- Reached from exactly one place: `store.runTier1ConversationTurn`, after normalizing the prepared conversation and before the system-prompt shape. Tier 3 never enters that function, so the text-protocol wire keeps its envelope blocks and separator examples byte for byte.
- Load-bearing consequence: sanitization can DROP messages, so the Tier-1 commit slices its tail at the WIRE length the turn reports (`wireMessageCount`), never at `preparedRequest.messages.length`. Slicing at the pre-sanitization length would silently discard the assistant reply and its tool results from persisted history.
- Bounded belt: if a sanitized turn still answers with separator prose and made ZERO tool calls, ONE corrective re-prompt is sent (`needsTier1CorrectiveRetry`, `TIER1_CORRECTIVE_RETRY_LIMIT = 1`, decided from the loop's own `turns` record, never from prose). The coaching turn is scaffolding: it is filtered out of the persisted message list so the human never scrolls past words they did not write. Without it that turn ended silently on the retired protocol.

### Execution Chip Exit (guaranteed exit on every tier)

- A chip may never be left waiting for a result that cannot exist. On Tier 1 nothing executes separator text — execution happens only through a typed tool call — so a reply that answers with separator prose ends the turn with no execution result coming.
- The surface tracks those assistant ids (`engineSwapDisplayOnlyMessageIds` in the store) and `thread-view.js` renders them as a TERMINAL `display-only` chip: label `Shown, not executed`, `visibility` icon (never the `sync` spinner), and `Nothing was executed.` in the output pane. It is not the old fallback either, which claimed `Executed N lines` for code that never ran.
- The id set is **DERIVED, not remembered**. `collectEngineSwapDisplayOnlyIds` is the one eligibility rule and `syncEngineSwapDisplayOnlyIds` applies it; `replaceHistory` calls it on every replace (before its `refreshPrompt: false` early return, which is the startup restore path), and the Tier-1 commit calls it over the composed history. Persisted ids survive verbatim (`assistant-<n>`), so commit and restore compute the same set from the same data and nothing is stored twice. A session-local set was audit blocker 1 of the P2 live hotfix: after a reload it came back empty and a never-executed message fell through to `Executed N lines`. The honest label is therefore **restore-safe**, not just session-stable.
- Eligibility is three conditions: assistant text, an EXECUTABLE separator, and NO execution results (the id's results override or a framework `execution-output` follow-up after it). A message that really executed keeps its executed label, so re-derivation can never relabel real executions as display-only.
- ONE pure resolver (`resolveExecutionCardState`) owns the label/icon/tone/pending-state decision, so the summary, icon, output pane and render signature cannot disagree. Precedence: streaming, then explicit rerun, then real results/errors (execution facts), then `displayOnly` (a FACT) ahead of `isConversationBusy` (an inference), then fallback. Results outranking `displayOnly` is what lets a rerun truthfully end the display-only claim instead of showing real output under a "not executed" label.
- The resolved pending state is part of the execute section's render signature. This is load-bearing: `isConversationBusy` is not in the message, so without it a row built mid-turn is reused when the turn ends and its spinner never stops — the exact live defect. A display-only row keeps ONE terminal signature across the turn end, so it also cannot flip back.
- A rerun that produces real results re-derives the set, which drops the id, so the card's label, icon and output pane all describe the execution (audit non-blocker 2). The set is cleared where the history it describes is cleared (chat clear, compaction).
- Eligibility uses the SHARED fence-aware separator test (`findExecutableSeparatorIndex`); a fenced separator is display text and is never reported as an unexecuted execution. A second copy of fence logic here is the BUG-007 anti-pattern.
- Tier 3 is untouched: it executes for real, so its chips still resolve through execution results (streaming, busy-no-results, rerun, success, error and settled fallback states are asserted byte-identical).

### Streaming Assembly And Sequential Parallel Dispatch (P3)

- Tool turns STREAM. The P2 boundary (non-streamed tool turns, because the surface reader dropped `tool_calls`) is retired and must not return: `tier1-session.js` requests `stream: true`, `transports.js` applies ONE stream rule to tool and text turns alike, and `tests/engine_swap_transports_test.mjs` pins both the streaming tool turn and an explicit `stream: false` being honoured.
- `stream-assembly.js` is the ONE assembler and is a pure leaf (no imports, no I/O, no config). Argument fragments accumulate per call index as STRINGS; a call reports `argumentsComplete` only when its argument text parses as a JSON object AND it has a name. Nothing is parsed mid-flight, so a partial payload can never be validated, coerced or executed. Two further refusals live here: a call with no name, and every call of a turn the provider ended with `finish_reason: "length"` (a prefix can parse by luck, so a declared truncation refuses everything in that turn).
- Providers that omit `index` are handled by identity, not guesswork: an id change starts a new call and a bare fragment continues the current one, which is what keeps interleaved parallel calls in separate buffers.
- Truncation is decided from POSITIVE evidence only — an abort the transport reports, or `finish_reason: "length"`. A missing `[DONE]`/`finish_reason` is NOT proof of a cut stream (providers differ), and inventing a refusal from it would reject healthy turns.
- The surface reaches the assembler through ONE SSE parser: `api.js` gained a raw-payload hook shared by the text and tool paths, and `streamOnscreenAgentToolTurn` owns fetch/URL/auth and returns the assembled result. A provider that ignores `stream: true` answers one JSON body, which the same assembler consumes — one code path for both behaviours, never a second parser.
- `extractToolCallsFromCompletion` accepts BOTH the assembled result and a raw completion payload, and copies `argumentsComplete` through unchanged. The assembler is the ONE owner of completeness; the session must not re-derive a second opinion.
- SEQUENTIAL PARALLEL DISPATCH: several calls in one turn are announced in ONE assistant message and executed one after another in returned order, never concurrently. One-call turns behave exactly as before. Load-bearing consequences, each tested:
  - every announced `tool_call_id` is answered exactly once, and the persisted tail replays into a valid sequence (`assertValidToolCallAdjacency`);
  - a failure mid-batch answers its own call with the structured error and the remaining calls STILL RUN (the difference between "this call failed" and "the turn failed");
  - a HELD destructive call ends the turn, and its later siblings are answered as `deferred:` rather than left dangling;
  - a call whose `argumentsComplete` is false is refused BEFORE it enters the message list (coaching turn, nothing announced), because an id we cannot answer honestly must not be announced at all;
  - stop is honoured between ITERATIONS, not between the calls of one turn (the P2 audit N1 contract and the surface's "Stopping after the current step..." wording).
- Audit-2 note N2 is wired: the repeat note (`buildRepeatErrorNote`) now escalates on EVERY failure path — dispatch errors, the incomplete-arguments refusal, and the batch coaching — so a model repeating one mistake is told how many times it has repeated it. Cap behaviour is unchanged.
- `tests/engine_swap_stream_assembly_test.mjs` is the assembler's owning suite: fragment splitting (4+ deltas, single delta, empty args, interleaved parallel calls, no-index providers), the no-dispatch-on-partial property, `finish_reason: "length"` refusal, and the extractor carrying a negative verdict through unrecomputed.

### Tier 1 Surface Paint And Streaming Preview (owner-reported, 2026-10-27)

- TWO live symptoms, ONE surface-owner each. Neither is a model problem and neither is fixed in this layer's loop:
  - **The user's own message did not appear until the reply did, and a fresh chat stayed blank until the first reply.** The Tier 1 branch of `store.runConversationLoop` rendered BEFORE the user's turn entered `this.history`. `render()` draws `getRenderHistory()`, which reads `this.history`, so the pre-request paint drew the PREVIOUS turn; on a fresh chat the history was empty, `thread-view.js:1629-1631` took its empty-state early return, and nothing was drawn at all. Tier 3 above it has always written history before rendering.
  - **Assistant text appeared all at once.** `api.js` already reports every text delta through `onDelta`, but both Tier 1 `sendCompletion` closures passed only `{requestBody, settings, signal}`, so the transport buffered the prose and the assembler returned it in one piece. This loop emits no delta event (`tool-turn-loop.js:195` is `assistant-turn`, only AFTER `sendTurn` resolves), so the surface is the only place a fix can live.
- CONTRACT: a Tier 1 turn writes the user's turn into history BEFORE it renders, and every render it performs receives a non-empty projection. Parity with Tier 3 is the invariant, not a coincidence.
- CONTRACT: a streamed reply paints through ONE preview slot (`store.engineSwapStreamingPreview`) that is added to the RENDER projection in `render()` and NEVER to `this.history`. That separation is load-bearing, not tidiness: history is what `persistHistory` serializes, what `syncEngineSwapDisplayOnlyIds` derives from, and what a reload replays, so a half-streamed reply must be structurally unable to reach any of them. A preview in history would also break the reload determinism guarantee of the chip-exit derivation (audit blocker 1) by deriving a `Shown, not executed` id for a message the user never received.
- The slot is RESET per request (a previous iteration's narration must not concatenate onto this one) and CLEARED in the turn's `finally`, so commit, hold, error, stop and a thrown transport all exit through one clear. The reserved id `engine-swap-streaming-preview` lets the existing row patch replace that row rather than appending a second one.
- Paint reuses the Tier 3 seams — `setStreamingAssistantStatus`, `maybeShowCompactStreamingAssistantBubble`, `scheduleStreamingMessageRender` — rather than adding a second streaming mechanism. Stop is untouched: the same `activeRequestController` signal still reaches the fetch, and no second stop source is introduced.
- Surface fixes never reach into this layer: no loop event, no session hook and no transport signature changed for either fix. The delta hook already existed; it simply was not passed.

### Shadow Artifacts (`ca.shadow-diff/1`)

- Three artifacts: `manifest.json` (one per run), `sessions.jsonl` (one line per compared turn), `summary.json` (the gate).
- The diff enum is closed: non-failing `match`, `split`, `merge`, `fallback-run-code`, `suppressed-display`; failing `unmapped`, `order-divergence`, `extra-call`, `missing-call`. The gate passes iff all four failing classes are zero, and counts always report in full.
- Display detection reuses the shared `execution-blocks.js` fence classifier. A second copy of fence logic is the BUG-007 anti-pattern and is forbidden.
- Normalization is shared with the lab side: own-user path collapse, recursive key sorting, code compared by SHA-256 plus first line, and payload-bearing argument values redacted to `{ omitted, bytes, sha256 }`. Code and file contents are never embedded whole.
- Artifact emission takes an injected sink. This layer performs no I/O of its own; the lab harness owns placement.

### Purity And Runtime Neutrality

- These modules are shared by the browser and by `node --test`. No browser-only or Node-only globals: hashing uses `crypto.subtle` or an injected digest, and byte lengths use `TextEncoder`.
- Projection never evaluates the code it reads. Unreadable arguments fall back to a single `run_code` call instead of guessing.

### Chat-Surface Grouping, Provisional Chips, Preview Markdown, Commit Race (owner-approved polish, 2026-10-27)

Four surface-only contracts. ZERO engine, wire, prompt, history-writer, dispatch or gate changes: nothing here reaches the loop, the session, the transports or the persistence mapping.

- **Grouping is derived from the stored entry sequence** (`_core/visual/conversation/tool-run.js`). A run starts at a typed `tool_call` projection, continues over typed entries, and ends where the next announcement begins (a call AFTER a result). Narration between runs splits them by construction, because narration is not a typed entry. ONE row per run (`5 tool calls · 3 succeeded · 2 failed`), expandable to the SAME per-call chips, in stored order. The renderer side is `buildMessageDisplayGroups`' `tool-run` branch, gated on the `groupToolRuns` option so the order-contract suites and Tier 3 stay byte-identical.
- **Consent episodes are never grouped.** A block containing a held or deferred call is left ENTIRELY individual: its calls and their results are contiguous, so grouping only the calls before a hold would leave them summarizing as `running` forever (a claim about finished work), and splitting the block would reorder rows the user watched. Provisional chips are excluded for the same class of reason. Provenance lives in `typedToolOutcome` on the display projection, written by the shared reader (`classifyToolResultOutcome`, closed set `success | error | held | deferred | pending`), so no consumer string-matches prose.
- **Expanded state lives outside the DOM** (`createToolRunOpenState`, held on the store) and is part of the run's render signature, because the thread view REBUILDS rows as results land: a `<details open>` boolean living only on a node would be lost on the next patch. The run key is the run's **first id only** (`tool-run:<first-id>`): a key that also carried the last id changed the moment a result landed, i.e. exactly when the card had to survive, so expansion collapsed on settle (audit non-blocker c).
- **Provisional chips are projection-only.** `api.js` `streamOnscreenAgentToolTurn` gained an `onToolCallComplete` hook that fires per call whose streamed arguments COMPLETE; it asks the assembler's own pure `finish()` rather than re-deriving a second completeness verdict, and it dispatches nothing. The store records `{callId, name}` deduped by call id, and `chat-projection.js` renders each as a `running` chip (`sync`, never `check_circle` — its placeholder text parses as an execution message, which is why `resolveExecutionCardState` takes `isProvisional` ahead of the results-shaped branches). Every chip ends in a terminal state or disappears, in two layers: one cleanup site (`clearEngineSwapStreamingPreview`, called from `sealEngineSwapPreview` in the turn's `finally`) empties the array on commit, hold, error, stop, iteration cap and thrown transport, and the projection additionally drops any chip whose call id the committed history already speaks for.
- **The stranding guard reads the DISPLAY projection, not raw history.** `buildChatRenderProjection` matches committed calls by `typedTool`/`typedToolCallId`, which are added by `projectHistoryEntryForDisplay`; handing it raw stored entries (`kind: "tool_call"`) therefore matched nothing and the guard was inert in production while a pre-projected fixture kept its test green (audit blocker 2, 2026-10-27). The store now has ONE seam, `buildRenderHistory()` (project first, then append projection-only state), and `render()` uses it; the stranding test drives that seam with raw typed history, so reverting the order reddens it.
- **Progressive markdown is PREVIEW-only** (`_core/visual/conversation/preview-markdown.js`). The accumulated preview text is re-rendered through the shared markdown renderer each tick, so an unclosed fence grows as a code block; a renderer that throws costs ONE tick of plain text and never kills the paint; work is bounded at `PREVIEW_MARKDOWN_MAX_CHARS` (20000) beyond which the preview paints plain. `selectMessageContentPainter` is the ONE committed-vs-preview decision and the renderer dispatches on it, so the committed message still takes the pre-existing `createFormattedMessageBlock` and its output stays byte-identical to today.
- **The commit cannot draw the reply twice, and the guard is scoped to the TURN.** `buildChatRenderProjection` refuses a preview whose id is committed OR whose text THIS TURN already committed, so "one assistant message, one row" is a property of the projection rather than a promise about the order two call sites run in. `appendEngineSwapStreamingDelta` additionally drops deltas while the slot is sealed, so a late frame cannot recreate a preview beside the committed reply.

  The turn scope is load-bearing and was the audit's blocker 1. The first cut compared the preview against EVERY assistant message in the thread, so any chat that had ever said "Done." / "OK." / "Let me check." made every later preview of that phrase invisible until commit — the same paint-timing regression this campaign already fixed once. The boundary is DERIVED from the projection (`collectTurnCommittedAssistantTexts`): a turn is opened by an entry that is a user message AND carries no `typedTool`/`provisional` mark (typed tool rows and provisional chips also wear `role: "user"`), so committed assistant output for this turn is only what appears after it. With no such entry (fresh chat) the whole list is considered — the conservative direction for a guard whose job is preventing a duplicate row. The identity half is defence in depth, not the mechanism: production preview ids are the reserved constant `engine-swap-streaming-preview` and committed ids are `${role}-${Date.now()}-${random}`, so they cannot collide; the check is kept so a future caller that hands the preview a real message id fails loudly.

All of this lives on the SURFACE side of the bridge (`_core/onscreen_agent/chat-projection.js`, `_core/visual/conversation/*`). Nothing here dispatches, executes, or persists.
